Kestrel Bank — architecture diagrams

Open this file in a browser. The source for each picture is in docs/diagrams. The written version is docs/architecture.md.

1. Runtime

The browser talks only to Vite. Vite proxies /api to Express. Express owns SQLite. ChatGPT or Claude is called only when a key is set.

flowchart LR
  browser["Browser React 19"]
  vite["Vite :5173"]
  api["Express :4000"]
  db[("SQLite")]
  llm["ChatGPT or Claude"]
  browser -->|"cookie and pages"| vite
  vite -->|"proxy /api"| api
  api --> db
  api -.->|"only if an API key is set"| llm

2. Request path

Pages never write SQL. Routes validate with Zod. Services are the only layer that prepares statements.

flowchart TB
  pages["React pages"]
  apiClient["api/client.ts"]
  routes["Express routes plus Zod"]
  services["Services"]
  sqlite["better-sqlite3 prepared statements"]
  pages --> apiClient --> routes --> services --> sqlite

3. Data model

Money is integer cents. One transfer row plus exactly two ledger lines. The clearing account has no customer.

erDiagram
  CUSTOMERS ||--o{ ACCOUNTS : owns
  CUSTOMERS ||--o{ PAYEES : saves
  CUSTOMERS ||--o{ TRANSFERS : submits
  CUSTOMERS ||--o{ SESSIONS : has
  ACCOUNTS ||--o{ TRANSACTIONS : ledger
  TRANSFERS ||--|{ TRANSACTIONS : two_lines
  TRANSFERS }o--|| ACCOUNTS : from_and_to
  TRANSFERS }o--o| PAYEES : optional_payee

4. Transfer, exactly once

The idempotency key is checked inside BEGIN IMMEDIATE. The same key replays. A new transfer writes the debit and the credit together.

sequenceDiagram
  participant UI as TransferPage
  participant API as POST /transfers
  participant TX as BEGIN IMMEDIATE
  participant DB as SQLite
  UI->>API: Idempotency-Key and body
  API->>TX: executeTransfer
  TX->>DB: lookup customer plus key
  alt same key and same hash
    DB-->>UI: 200 replay, no second movement
  else new transfer
    TX->>DB: debit, credit, both balances
    DB-->>UI: 201
  end

5. Where the money goes

Own-account transfers stay inside the customer. A payee payment credits the bank clearing account.

flowchart LR
  subgraph ownTransfer [Own accounts]
    checking["Checking debit"]
    savings["Savings credit"]
    checking --> savings
  end
  subgraph payeePay [Saved payee]
    source["Customer debit"]
    clearing["Clearing credit"]
    source --> clearing
  end

6. Security on a protected request

Login, logout, and health are public. Every other banking route needs a session, then Zod, then a query scoped by customer id.

flowchart TD
  req["Protected /api request"]
  helmet["Helmet, 20kb JSON, no-store"]
  jsonCheck{"Mutation sent as JSON?"}
  session{"Valid session cookie?"}
  zod["Zod"]
  scope["SQL scoped by customer id"]
  req --> helmet --> jsonCheck
  jsonCheck -->|no| media["415"]
  jsonCheck -->|yes| session
  session -->|no| unauth["401"]
  session -->|yes| zod --> scope

7. Assistant

Three read-only tools, bound to the signed-in customer. No tool can move money. If the model call fails, the rules use the same tools.

flowchart TB
  user["Customer question"]
  loop["Agent loop, max 5 steps"]
  tools["Read-only tools closed over customer id"]
  data["Accounts, recent transactions, spending"]
  rules["Rule fallback if no key or LLM fails"]
  user --> loop
  loop --> tools --> data
  loop -.-> rules

8. Layer mapping

Routes are the inbound edge. Services hold the rules. SQLite, bcrypt, sessions, and the model call are the outside systems.

flowchart TB
  ui["React adapter"]
  http["Routes and Zod"]
  appLayer["Services"]
  rulesNode["Cents, ownership, idempotency, read-only tools"]
  infra["SQLite, bcrypt, sessions, ChatGPT or Claude"]
  ui --> http --> appLayer
  appLayer --> rulesNode
  appLayer --> infra

9. Client composition

Auth wraps the layout. Pages and the assistant panel both call api/client.ts.

flowchart TB

  pages["Accounts, history, transfer, receipt"]
  panel["AssistantPanel"]

  main --> auth --> app --> guard
  guard --> pages
  guard --> panel
  pages --> api
  panel --> api

10. Database startup

DATABASE_PATH defaults to memory. The schema is applied, then demo data is seeded only when customers is empty.

flowchart LR
  env["DATABASE_PATH"]
  open["openDatabase"]
  schema["SCHEMA_SQL and foreign_keys"]
  wal["journal_mode WAL"]
  seed["seed if customers empty"]
  app["createApp"]
  env --> open --> schema --> wal --> seed --> app
